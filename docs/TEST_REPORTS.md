## v0.5：业务断言驱动的 Bug 复现

### 修复后复测（2026-09-09）

本轮修复并关闭首次测试记录中的三项问题：

1. 将动作后的辅助状态读取改为容错采集。控件因切换页面或 DOM 更新消失时，记录当前页面或采集不可用提示，不改变已成功的动作结论；下一步场景断言正常执行。
2. visible / hidden 断言不再被通用“必须先找到且可见”检查截断。核心检查会等待目标出现；超时未出现或仍隐藏则判为失败。前置检查失败仍为受阻，多匹配仍为歧义，不误报已复现。导出测试同步调整定位前置逻辑。
3. 更新旧 GitHub 报告的草稿预期，并补充 generated / draft 文案和核心检查覆盖率对应的 Check 结论测试。

### 问题 1：动作成功后旧目标消失，证据采集反而终止流程（高优先级）

位置：apps/api/src/business.ts，executePlan 的动作后 observe(page, target)，当前约第 172 行。

复现：登录页点击 Register tab；注册表单显示，同时入口按钮移除。点击本身成功，但随后 observe 仍读取旧按钮，locator.evaluate 等待 4 秒超时，被同一个 catch 标为 blocked，注册表单输入步骤全部 skipped。

单独重复运行 switch 场景可稳定复现。导出测试没有这一步旧目标采集，因此可以完成注册表单输入；两条执行路径结论不一致。

建议：将动作后的辅助采集失败与动作/断言失败分开。入口因导航、DOM 更新消失时，采集当前页面状态或记录“原目标已消失”，不自动将成功动作降级为受阻。真正的下一步场景断言仍应独立执行。

### 问题 2：核心 visible 断言被通用定位前置检查截断（中优先级）

位置：apps/api/src/business.ts，第 98–99 行的 toHaveCount / toBeVisible，早于核心 assertion 分支。

复现：已确认目标场景，核心要求出现 Saved 提示，但页面未出现该提示。程序在进入核心 visible 检查之前就以定位失败返回 blocked，最终为 inconclusive，无法表达“指定提示未出现”。

建议：区分“操作目标找不到”和“核心断言要求目标出现但没有出现”。对用户确认过的 visible 检查，零匹配属于待验证的业务状态；多匹配仍应按歧义处理。适当保留场景前置校验，避免把未进入页面误判成 Bug。

### 问题 3：旧 GitHub 报告测试预期未同步（低优先级）

位置：apps/api/tests/github-publisher.test.ts:43。

测试使用没有 business 字段的旧记录，仍断言包含“Playwright 回归测试：已生成”。v0.5 实际显示“草稿 / 尚未验证”，符合新版对旧记录的保守处理。应更新旧记录预期，并另补有完整业务证据的 generated / draft 场景，而不是回退产品文案凑通过。

### 重跑方式

在项目根目录执行：

~~~sh
npm run check
npm run build
node scripts/verify-v05.mjs
node scripts/verify-v05-ui.mjs
~~~

定位单场景：

~~~sh
node scripts/verify-v05.mjs switch
node scripts/verify-v05.mjs missingMessage
~~~

前两个已知缺陷未修复前，浏览器验证脚本返回非零退出码是预期结果，不应删除断言来规避失败。

### 尚未覆盖

- 真实 DeepSeek 规划质量与模型故障降级。
- API 创建/存储/SSE 的完整端到端链路，UI 使用拦截响应。
- GitHub 真实 Check / 评论发布。
- 全设备矩阵、iframe、真实网站及复杂异步竞态。
- 导出文件在完整 Playwright runner / CI 环境下的类型检查与运行；本轮对导出测试体做了 TS 转换后实际执行，不等同于完整 runner 验证。
- 输入后长期延迟回滚、超时压力和全部敏感数据泄漏边界。

本次结果说明“输入能力验证”主线能够检出常见故障，但注册页切换是优先修复项。修复后应重跑上述两个失败场景及现有用例，再考虑完整发布验收。
